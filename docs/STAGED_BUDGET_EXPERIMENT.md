# 重新检验 More with Less：分阶段预算不等于普遍提速

结论：本次真实请求中，分阶段预算对 AI Studio 项目问题有帮助，对新加坡天气没有改善；也没有证据证明答案质量整体提高。因此实现保留为可选实验，默认仍为固定预算，不自动替换用户现有策略。

## 论文给出的启发及适用边界

论文：[More with Less: An Empirical Study of Turn-Control Strategies for Efficient Coding Agents](https://arxiv.org/abs/2510.16786)，本次阅读其 [v1 全文](https://arxiv.org/html/2510.16786v1)。

- 实验对象为 SWE-bench Verified 按仓库比例抽样的100个编程任务，使用 Claude 4 Sonnet、Gemini 2.5 Pro 和 GPT 4.1；不是联网事实问答，也没有测量 DeepSeek/PiCall。
- 它比较无限轮数、固定轮数+逐轮提醒、较小初始预算+一次扩展。固定预算采用基线轮数分布的25/50/75分位数，而不是任意指定“所有任务两轮”。
- 75分位固定预算报告约24%–68%的费用下降；动态策略报告进一步约12%–24%的费用下降。这里是编程任务费用/解题率，不能改写成 PiCall 延迟下降比例。
- 启发是减少没有信息增益的模型往返：每轮都重新输入不断增长的历史，累计 token 成本可能快速增长。应给简单问题较小初始目标，把更多工具调用留给确实存在证据缺口的任务。
- 作者明确承认每个实验没有重复3–5次，并且关闭了提示缓存；本次官方服务仍可能使用前缀缓存。因此论文的费用比例和量化阈值都不能直接照搬。

## 实现

新增 `researchBudgetMode`：

- `fixed`：默认，保持原有提醒文字与硬上限。
- `staged`：实验。预算提醒开启时，以最多2轮为初始软目标；持续未完成的请求进入一次扩展阶段，最多规划到 `maxToolRounds - 1`，留出生成最终答案的机会。

网页入口：服务设置 → 搜索与网页 → 任务预算 → 取证预算策略。关闭预算提醒则两种模式都不注入预算提示。修改模式后新建会话。

阶段从 Durable 持久轮数推导，不修改 SDK 硬上限、不重置截止时间、不创建额外 run 续命。默认8轮上限和300秒期限保留。与论文的硬截断后增加额度不同，这是适应 Pi Durable 终止语义的软规划版本；模型可以不遵循软目标，硬上限仍生效。

提醒包含基于证据的收尾、独立且输入已知的查询批处理、时效核查以及歧义区分；没有额外裁判模型、问题专用 URL 或隐式天气工具。新增 timings 阶段字段便于复盘，不能把阶段字段等同于模型真正遵循了目标。

旧配置缺少模式字段时按 fixed 处理，其执行指纹不变；staged 会改变执行指纹。用现有恢复逻辑阻止旧会话在配置变更后继续执行。

## 真实测试

时间：2026-11-11，Asia/Shanghai；基线源码 `88cd2042435eb15a5aa9c647fb193410f78bedbe`（包含新的 Jina/HTTP 并行竞争）。模型为官方 `deepseek-flash`；两组使用相同网关、搜索配置、输出上限、8轮硬上限、300秒期限。`httpTools=[]`，不使用上次实验的天气或 Google 专用工具。

原题各3次，顺序为第1/3轮固定→分阶段，第2轮分阶段→固定，全部新会话且顺序执行。另加一道要求至少两个官方来源的 Cloudflare DO/KV 比较题，每组一次，检查软目标没有强迫复杂任务两轮结束。

在发现回答冗长后又探索“分阶段+范围/简洁提示”，同样每题3次、复杂题一次；这是后验实验，全部在主对照后执行，不是严格随机对照。共21次请求，21次返回 completed；这不代表21次事实完全正确。

| 问题 | 固定预算，秒 | 分阶段预算，秒 | 中位数变化 |
| --- | --- | --- | --- |
| 今天新加坡天气怎么样 | 11.985 / 5.898 / 6.091 | 8.920 / 11.178 / 6.105 | 6.091 → 8.920，慢46.4% |
| google aistudio 中项目是只能有一个绑定google cloud 吗？ | 14.619 / 25.306 / 20.583 | 15.961 / 10.815 / 10.050 | 20.583 → 10.815，快47.5% |
| 比较 DO/KV 一致性和场景，至少两个官方来源 | 23.100（一次） | 21.623（一次） | 单样本不足以判定收益 |

计时为服务端 `run.elapsed_ms`，覆盖受理至最终答案完成。客户端每500ms查询一次，额外轮询等待单独保留。

模型阶段与 token 中位数：

| 问题 | 固定 model_ms → 分阶段 model_ms | 固定 total_tokens → 分阶段 total_tokens | 固定工具轮数 → 分阶段 |
| --- | --- | --- | --- |
| 天气 | 5152 → 6702 | 6693 → 7239 | 3/2/2 → 2/3/2 |
| AI Studio | 15506 → 8939 | 30546 → 11421 | 2/4/4 → 3/2/2 |

AI Studio 的收益主要伴随更少的模型往返和历史 token；天气原本多数已是两轮流程，没有稳定减少空间。token 含供应商报告的缓存使用，不能直接当作账单费用降幅。

后验“分阶段+简洁提示”：天气中位数15.491秒，AI Studio 16.997秒；均差于单独分阶段。复杂题20.274秒但只测一次。未将该提示变成产品默认或推荐配置；完整提示及逐次输出保留在数据文件中，避免只报告成功结果。

## 答案质量复核

本次人工检查原始答案、引用的官方文档、天气时间戳及单位，没有使用另一个模型打分，也没有将 completed 当作正确率。

- 天气确实取得当日信息：官方两小时接口有20:36:43更新、20:30–22:30有效的预报；Time and Date 页面区分20:00观测与页面当前时钟。日期、观测时刻、预报有效期应分别看待。
- 固定预算第一次把全岛“多云预报”写成“没有降雨”；分阶段第二次虽取得官方数据，仍给出“出门一般不用带伞”的过度推断。这说明预算提醒不能保证正确的事实解释。
- 后验简洁提示第二次出现明确错误：把官方相对湿度60%–95%写成“降雨概率60%–95%”；第三次又出现“不用带伞”。因此不推荐该组合，即使部分答案变短。
- AI Studio 各组大体覆盖“账号可导入多个项目、每个 key 归属一个项目”，但仍出现“任意多个”“唯一限制”或扩展到未经充分限定的 Build 部署等问题。不能据此宣称质量提高。
- DO/KV比较均完成多来源回答，分阶段用了3轮而非被两轮截断。但双方都有值得纠正的技术表述，例如把DO单线程概括为自动避免所有异步竞态，或将KV“60秒甚至更久”在结尾简化成“最长约一分钟”。仅完成复杂问题不等于通过严格事实验收。

## 对 PiCall 的建议

1. 把先少后多作为可选择的策略，不把低预算硬套在所有问题上；通过更大的题集测量成功率、质量、轮数与耗时，再调整目标。两道题不足以估计可靠分位数。
2. 天气等结构明确的实时事实，优先沿用已测的官方结构化工具。下一步应让取值字段、单位、更新时间与最终陈述绑定，阻止湿度被写成降雨概率，而不只是增加文字提醒。此轮没有实现自动事实验证器。
3. 产品规则问题使用官方文档，明确 key/项目/账号/部署实体；证据充分就结束，避免把相关但未问的旁支变成额外工具轮次和额外错误来源。
4. 分别优化工具往返、模型输出和来源解析；多加提示、压缩字数、降低硬轮数都不是可靠的单一解法。保留复杂问题扩展能力和诚实的证据不足说明。

上一轮专用工具方案的4.5秒/5.0秒与本轮不是同时间/同源码的对照，不能宣称本次进一步超越了它；本轮测试的是通用调度策略，不是专用来源替代。

## 验证与复现

自动化验证：104项测试通过（共享工具30、本地49、workerd25），另通过语法/类型检查、浏览器配置保存与刷新、Worker dry-run构建及独立 npm 包真实 SQLite 启动。新增测试覆盖扩展阶段、保留最终回答机会、小硬上限、提醒关闭、SIGKILL恢复、默认指纹兼容和显式模式变更。

要复测，分别使用固定/分阶段配置的两个独立数据目录启动服务，保持其余配置完全相同，使用新会话提交上述原题并保存最终 `/v1/runs/{id}`。更可靠的下一轮应随机化顺序、扩大题集，并预先定义可核验的质量标准；不要仅比较某一次最快结果。

默认策略为 fixed，staged 为可选实验。提交代码不会部署生产服务，也不包含凭证。
