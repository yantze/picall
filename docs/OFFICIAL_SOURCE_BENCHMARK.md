# 官方来源工具：真实模型延迟实验

2026-11-11 在 Linux、Node.js 24.22.1、DeepSeek 官方 `deepseek-flash` 上测试。应用版本为 `237a5e0cf704e77e764d6c43c3c88f587ad4851d`。后续 `53299d0` 修改了正文读取竞争顺序；下面的数据不是该后续版本的测量结果。

## 结果

通过现有 `httpTools` 和 `additionalSystemPrompt` 配置，给两类问题提供直接覆盖事实的官方来源，减少搜索、正文提取和模型往返。

| 原题 | 基线三次完整耗时（秒） | 优化后三次（秒） | 中位数变化 |
| --- | --- | --- | --- |
| 今天新加坡天气怎么样 | 30.596 / 7.425 / 12.617 | 4.479 / 4.277 / 4.471 | 12.617 → 4.471，减少 64.6% |
| google aistudio 中项目是只能有一个绑定google cloud 吗？ | 35.539 / 17.575 / 27.804 | 7.000 / 4.848 / 5.004 | 27.804 → 5.004，减少 82.0% |

耗时为服务端 `run.elapsed_ms`，覆盖受理至最终答案完成，不是首 token 时间。客户端每秒查询一次，因此 `client_ms` 还包含轮询等待。

最终配置六次请求全部完成，工具错误为零；每次为一轮工具、两次模型请求。天气基线为 6/2/2 轮工具，AI Studio 基线为 7/2/4 轮工具。[逐次测量数据](examples/official-source-benchmark.json)保留了服务端/客户端耗时、模型耗时、请求数、工具轮数及 usage。

## 配置与应用

[配置示例](examples/official-source-tools.json)不包含凭证，是可选的场景专用配置，不会自动改变应用默认行为。

- `singapore_weather_2h` 与 `singapore_weather_24h` 直接 GET 新加坡官方预报 JSON，可同轮调用。
- `google_ai_project_docs` 直接 GET 官方项目与 API key 文档。旧 `ai.google.dev/gemini-api/docs/api-key` 地址在测试时返回 301，因此配置已验证的规范地址 `https://aistudio.google.com/docs/api-key`；保留自定义工具禁止重定向的保护。
- 附加提示要求检查有效期、区分预报与实况、区分账号与项目/API key，并在证据充分时收尾。来源过期、缺失或冲突时继续搜索。

在网页服务设置中，将示例 `httpTools` 的三个对象合并到现有自定义 HTTP 工具数组，避免重名并保留其他工具；将 `additionalSystemPrompt` 合并到附加系统提示字段后保存。也可停止本地服务、备份自己的 `config.json` 后合并这两个字段，再启动服务。不要用这个局部示例替换完整配置。配置变更后使用新会话。

模型网关使用 `https://api.deepseek.com/v1`，模型 ID 以官方 `/models` 返回值为准。凭证通过自己的服务设置提供，不提交到 Git。云端开发机器若需要环境代理，启动 Node 时使用 `NODE_USE_ENV_PROXY=1` 并保留环境提供的代理与证书信任。

## 正确性检查

天气工具在测试时返回了当天 19:36:37（UTC+8）更新、19:30–21:30 有效的两小时预报，各区均为多云。24小时预报有效期为 11 月 11 日18:00至12 日18:00，温度24–34°C，当晚多云、次日午后部分区域雷阵雨。最终答案能够标注日期/有效期，并说明这是预报而非实时观测。不能把跨日概况直接说成“今晚雷阵雨”，也不能把多云推断为保证不下雨。

Google 官方文档支持：AI Studio 可导入多个 Cloud 项目；每个 Gemini API key 归属一个 Cloud 项目。页面显示上限不能解读为只能绑定一个，也不能反推导入数量无限。如果问题实际涉及 Build 应用的部署目标，需要另查部署文档，不能由 API key 文档推断。

初版优化的四次试跑暴露了天气保证性措辞、无依据的“导入数量不限”和 Google 文档重定向问题，修正后才进行最终六次测量。个别最终答案仍会使用“唯一限制”或“限制只是页面层面”等偏宽措辞；本实验验证核心事实，不构成完整的项目限额或组织策略审计。

## 复现与边界

1. 用相同模型和网关测试原配置与示例配置，保持8轮上限、300秒期限、8192输出 token 上限及预算提醒开启。
2. 每次提交原题，创建新会话，记录 `GET /v1/runs/{id}` 的最终状态、completion、elapsed_ms、timings 和 usage。不要复用已完成 run。
3. 每题每组至少重复三次，核验引用内容、日期与结论后再比较耗时。未来测量建议随机交替两组，记录冷/热缓存条件。

本次共16次真实回答：6次基线、4次初版试跑、6次最终优化。统计仅使用基线样本1/2/3与最终优化样本3/4/5。最终版本主要在基线之后运行，不是严格随机交叉实验；模型前缀缓存、网站缓存和网络波动可能影响差值。样本量不足以可靠估算p95，不能将这两道题的降幅推广到任意研究任务。

这是专用来源工具与提示词的组合优化，没有隔离各自贡献，也没有证明预算提醒单独产生这些收益。它不依赖降低轮数或截断答案，未改变生产默认配置。
