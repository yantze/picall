# 研究效率：预算提醒与耗时基线

本轮落实 [More with Less](https://arxiv.org/abs/2510.16786) 对 PiCall 的第一阶段启发：使模型感知现有预算，并建立可对照的延迟数据。论文基于编程任务，费用下降比例不能视为 PiCall 的实际提速比例。

## 行为

- 默认 `budgetReminders=true`，管理网页「搜索与网页 → 任务预算」可关闭。单一研究模式、默认 8 个工具轮次及 300 秒截止时间保持不变。
- 从 Durable `LiveDoc.run.turns` 读取持久轮数，每次 generation 请求重新计算剩余时间。恢复不会获得新的轮数或期限。
- 提醒要求证据直接回答问题后收尾，只为缺失、过期或矛盾事实补查；预算压力不能成为编造事实或引用的理由。
- `beforeRequest` 只给这一次上游请求添加系统元数据，不改用户输入，不累积进会话历史，不拼入最终 API 正文。
- 硬上限仍由 SDK 执行。尤其不能将 maxTurns=2 当作“搜索、阅读后还能自动回答”：触及上限的工具轮执行完会直接 turn_limit。
- 预算提醒与观测层不自动扩展预算、不调用额外的裁判模型，不改变既有 provider 策略、超时或正文预览。后续动态策略和内容抽取应基于实测决定。

正文读取同时请求 Jina 和直接 HTTP，首个完整且通过校验的正文立即胜出，并取消其他请求。2 秒内没有有效正文时启动 TinyFish；两项提前均失败时立即启用 TinyFish，缺 key 时跳过。只收到响应头不算完成，空正文和验证码页面不算成功。该策略可能产生重叠请求和额外费用；耗时观测同时覆盖胜出及已结束的取消请求，不将重叠耗时相加。

开启提醒的默认值不改变旧执行配置指纹，兼容已有任务和会话；显式关闭属于执行配置变化，需新会话。旧云端加密配置缺少该字段时默认开启。

## 读取指标

`GET /v1/runs/{id}` 和网页管理查询返回可选 `timings`；JSON/SSE chat completion 合同不变。运行中的查询也可返回已记录的部分指标。未进入模型阶段的任务或旧结果可能没有此字段。

| 字段 | 含义 |
| --- | --- |
| model_requests / model_responses | 进入 generation 请求阶段的次数 / 已观测终态的次数；包含 Durable 重试，不是供应商计费次数 |
| model_ms | 已完整观测的模型阶段累计耗时，含少量 SDK/观测开销，不含重试退避 |
| tool_rounds / hard_limit | 实际持久工具轮数 / 硬上限；不是工具函数调用数 |
| models | 最多保留最近 256 次请求的起点、SDK attempt、此前轮数、终态、耗时及数值用量 |
| incomplete_model_requests | 尚未完整观测的请求数；任务结束时未闭合记录标为 interrupted，耗时未知 |
| tools[name] | 完成的工具调用次数、错误、缓存命中和累计阶段耗时 |
| providers[name] | 结束的 HTTP 调用次数、失败/取消、响应头等待 headers_ms 和完整响应 elapsed_ms |

模型或 HTTP 请求在进程终止前没有记录终态，其耗时不能补算；不把重启停机时间算成模型耗时。已有 service_calls 记录请求尝试，因此可能大于 providers 的完整观测次数。每次模型返回的观测 usage 也可能与 SDK 最终提交的 run usage 存在崩溃窗口差异，账务仍以供应商记录为准。

provider 的响应体流保持背压和取消传递；大小、类型及重定向限制继续生效。提供者 HTTP 成功但正文解析/验证码识别失败时，原有诊断事件仍负责解释内容问题，不能仅看 HTTP 错误数判断证据质量。

指标按 run 隔离，只有标识、计数、数值用量和时长，不保存提示词、URL、响应正文、密钥或请求头。本地使用独立 `picall.timings` 文档，避免每次观测重写网页全文缓存；云端使用独立 timings 键。日志使用同一份脱敏事件，观测写入或日志错误不增加另一套模型重试。

并行工具/HTTP 的时长会重叠，model_ms、工具耗时和 provider 耗时不可直接相加。端到端比较使用 run.elapsed_ms，并同时记录客户端 time_total。

## A/B 实测

1. 使用同一模型、网关、硬轮数、期限及代表性问题；一组关闭提醒作为基线，一组开启提醒。
2. 每组使用新会话和不同幂等 key，不复用上一组结果。组内任务结束后再切配置，避免配置变化干扰恢复。
3. 覆盖简单实时事实、多源比较及深度研究，每题重复多次；区分冷/热缓存，并尽量减少实时内容变化造成的差异。
4. 同时统计 p50/p95 完成时间、token、工具轮数、超时、事实正确率、引用支撑率及有证据却过早拒答的比例。不能以更少 token 或 HTTP 200 单独判定优化成功。
5. 本轮模拟测试验证计数、提示、恢复和测量正确性，未证明真实模型的速度或质量收益；需用户自身凭证完成真实对照。

## 分阶段取证预算

默认仍使用 `researchBudgetMode="fixed"` 的原有提醒。网页「任务预算 → 取证预算策略」可选择实验性的 `staged` 模式；它在预算提醒开启时，先以最多2轮工具调用作为软目标；证据不足时进入一次扩展阶段，最多规划到 `maxToolRounds - 1` 轮，为最终答案保留一次模型请求。默认8轮硬上限仍由 SDK 执行，期限和重试策略不变。提醒关闭时仍保留耗时测量。

阶段根据 Durable `LiveDoc.run.turns` 推导，重启不会重新获得初始额度。`maxToolRounds=1` 时没有可保证随后生成答案的工具轮次，提醒直接要求基于现有证据回答或说明无法验证。模型可能不遵循软目标，硬上限仍然生效。

这是对论文“先少量预算、必要时扩展”的适配，不是其硬截断后增加额度的直接复现：Pi Durable 在硬上限工具轮结束时就终止，不能将硬上限先设为2再等待模型作答，也不能另建 run 绕过原始期限。当前实验的2轮目标是工程假设，没有用这两个问题估计可靠的25/50/75分位数。

提醒还要求同轮批量执行已知输入且相互独立的查询、只为具体证据缺口补查，并在输出前检查时效、预报/实况和歧义。它不引入额外裁判模型，不能替代事实核验。新增 `timings.budget_strategy`、`budget_phase`、`initial_round_target`、`round_target` 仅记录调度元数据；它们不是实际消耗的硬预算，也不表明扩展阶段必然调用了更多工具。

旧配置缺少模式字段时按 fixed 处理，执行配置指纹兼容旧值；显式启用 staged 会改变执行指纹，必须新建会话。修改模式不会给旧任务悄悄增加预算。

真实分阶段对照及负面结果见[重新检验 More with Less](STAGED_BUDGET_EXPERIMENT.md)：AI Studio 样本变快，天气样本变慢；没有验证整体质量提升，所以保留 fixed 为默认值。
